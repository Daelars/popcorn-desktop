# Popcorn Time Desktop

Electron + React rewrite of Popcorn Time. Package manager: **pnpm**.

## Read first

- `CONTEXT.md` — domain glossary (StreamSession, PlaybackTarget, Catalog, Library, …). Use these terms.
- `docs/adr/` — architectural decisions. If a change contradicts one, say so instead of silently overriding.
- `docs/agents/` — issue tracker (GitHub issues on `Daelars/popcorn-desktop`), triage labels, domain-doc conventions.

## Layout

- `src/main/` — Electron main process (Effect services).
- `src/preload/` — the bridge exposed to the renderer.
- `src/renderer/` — React UI. Imports only from `src/shared/`, never `src/main/`.
- `src/shared/` — types, IPC contracts, tagged errors, settings metadata.
- `legacy/` — the old NW.js app (outside `src/` on purpose). Reference only; don't modify. Its `styl/`,
  `language/` and `settings.js` are inputs to `pnpm generate`. Internal paths still say `src/app/`; ignore them.

## Main process rules (`src/main/`, `src/shared/`)

- Services are Effect `Layer`s composed from one root (ADR-0001).
- `Effect.runPromise` only at IPC handler boundaries (exception: the smoke harness in `src/main/smoke.ts`).
- Failures are tagged errors from `src/shared/errors.ts`; never throw strings.
- Scoped resources use `Scope` + `acquireRelease`, never manual cleanup flags.

## Commands

- Verify cheaply first: `pnpm typecheck`, `pnpm lint`, `pnpm test <path>`.
- Full `pnpm build` only when needed to verify the change, when asked, or when nothing cheaper works.
- Don't start `pnpm dev`; assume one is already running.
- Don't hand-edit `resources/themes/`, `resources/locales/` or `resources/images/flags/`; they're
  generated by `pnpm generate`.

## TypeScript

- No `any`. Avoid `as` outside trust boundaries; prefer `satisfies`, narrowing, and inferred types.
- Model states as discriminated unions; derive types from schemas/constants instead of duplicating them.
- No one-line wrapper functions that only cast.

## General

- YAGNI. Simple beats clever, but propose bold changes when they pay off.
- Short comments above functions/modules explaining use; keep them in sync when code changes.
- Ask before destructive actions the user didn't request.

## Questions are read-only

If a message asks rather than instructs ("should we", "why does", "is it possible", "how hard would it be"),
answer it and don't edit files. If the fix is trivial, offer it and wait for a yes.

## Tests

- Don't create new test files, helpers, or fixtures without explicit approval. "Fix/implement/verify" is not approval.
- Prefer running existing tests and runtime checks. Test observable behavior, not source shapes.
- No smoke tests for the sake of it, and no "regression tests" for deleted features.
